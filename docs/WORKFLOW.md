# 工作流程

使用者給一個**目標**、一個**方向**，或一顆天馬行空的**種子**。Agent 負責到底：自己判斷怎麼做，上網查資料，挑工具，實作，舉證，試錯，一路推進到完成線。只有真正需要使用者的時候才回來問。

## 1. 接案

1. 看 `projects/`。使用者點名的專案，或目標跟既有專案相同，就接續那個專案：先讀它的 `PROJECT.md` 與 `LOG.md`，從「下一步」開始做。舊專案如果還寫著用 `workbench.py status` 接續，就讀它資料夾裡現有的文件，再把 PROJECT.md 補成文末的格式，並補一份 LOG.md。
2. 新目標就建 `projects/<slug>/PROJECT.md`（格式見文末），把使用者原話一字不改貼進「原始想法」。之後的補充往下追加，原文保留。

成果放哪裡：屬於別的 repo 就直接在那個 repo 開 branch 做，紀錄留在這裡的 Project 資料夾；沒有既有 repo 就放 `projects/<slug>/workspace/`。

## 2. 判斷是哪一種輸入

| 使用者給的 | 你要做的 | 進入推進迴圈的條件 |
|---|---|---|
| **目標**：要做到的結果 | 自己把目標寫成**完成線**（一條一條可檢查的驗收條件），寫進 PROJECT.md 後直接開工 | 完成線寫好就開工，不必等使用者批准 |
| **方向**：想往哪裡走，終點未定 | 先查資料，提出 2–3 條候選完成線（各附代價與你的推薦），請使用者挑一條，或改成他要的 | 使用者選定完成線，之後就照目標處理 |
| **種子**：天馬行空的想法 | 自己先上網研究可行性、類似作品與技術路線；只問查不到的事（使用者的偏好、可用資源、限制），一輪最多 5 題，每題附上你的建議答案。接著提出 2–3 個具體概念，每個概念都附上它的完成線 | 使用者選定概念，就照目標處理 |

分不出是哪一種時，當成比較成熟的那一種處理，並在回覆裡說明你是怎麼判斷的。使用者明確說要深入討論時，改用 `grilling` 的節奏（要保存決策就用 `grill-with-docs`，它是讀檔型 Skill，直接讀 `.claude/skills/grill-with-docs/SKILL.md`）；這時以 grilling 的一輪規則為準，不受 5 題的限制。

## 3. 挑工具

讀 [library/CATALOG.md](../library/CATALOG.md)，挑出這次用得上的 Skills 與角色。目錄裡標「讀檔」的 Skill，直接完整讀它的 SKILL.md 再照做。專業角色用關鍵字搜尋 `library/agents/INDEX.md`。挑好的工具和挑選理由寫進 PROJECT.md 的「工具」欄。做到一半發現需要新工具就加上去，同樣記下理由。

使用角色的方式：
- **原生角色**（`.claude/agents/`）：直接當 subagent 類型開。
- **角色庫**（`library/agents/`）：開一個 subagent，請它先完整讀那份角色檔，再以那個角色做指定的事。
- 每個 subagent 都要拿到：目標、完成線、工作目錄、要用的 Skills，以及回報格式（做了什麼、證據、還沒驗證的部分）。
- 彼此獨立的工作可以同時開幾個 subagent 平行做。

## 4. 推進迴圈

照下面四步一直循環，直到完成線每一條都有證據：

1. **查**：缺的知識自己找，順序是官方文件、原始碼、網路搜尋，再來是實際試跑。把查到的來源記下來。網路被環境擋住時，先換其他來源；真的需要那個網站，就說明是哪個網站、為什麼需要，請使用者開放網路。
2. **做**：每次推進一小步，做完 commit，讓每一步都能退回。commit 和 push 到這次工作用的 branch 可以直接做，不必問。
3. **驗**：用最貼近真實使用的方式驗證，例如測試、建置、實際執行，或在授權範圍內打開瀏覽器看。要留證據：指令與輸出、截圖、數據。
4. **修**：失敗就找出原因，換個做法再試，把試過的做法和結果寫進 LOG.md。

**卡關**是指同一個問題（包含驗收時被判 FAIL 的同一條完成線）換了三種做法都沒進展，或必須取得只有使用者能給的東西。卡關時先把已做的部分保存下來，向使用者說明狀況、列出你想得到的選項並附推薦，然後先做其他不受阻的工作。

以下情況要先問使用者，問了再做：
- 需要帳號、金鑰或付費。
- 部署、發布、推到 main 或預設 branch、開 PR、推到別人的 repo，或其他對外寫入（例如建立 GitHub issue、發訊息）。
- 刪除或覆寫使用者的資料，或其他不可逆的動作。
- 純屬個人喜好、而且會改變方向的選擇。
- 想把範圍擴大到完成線以外。

除了上面這些，其他判斷都由你自己決定，並在 LOG.md 記下理由。

### 切細派工（壓低交辦與交付成本）

主 session 負責想清楚與切細，執行交給 sonnet；驗收不可省略。

1. **切票**：主 session 照 `to-tickets` 的格式，把工作切成 `projects/<slug>/issues/NN-<slug>.md`。每張票只完成一個可驗證的行為，必須自足：要做什麼、可能碰到的範圍、不做什麼、驗收指令（可直接執行、看結果就知道 PASS／FAIL）、被哪張票擋住。
2. **明確度關卡**：執行者不必再做判斷就能完成的票，才可以派出去。需要取捨、設計或問使用者的，留在主 session 解決（必要時用 `grilling`），解決後再寫進票。
3. **派工**：只派沒有被擋住的票。派工訊息只寫票檔路徑和工作目錄，不重抄內容：`Agent(subagent_type: "implementer")`（角色預設 `model: sonnet`）。彼此獨立的票可以平行派。
4. **回報要短**：commit hash、跑過的驗收指令和結果、沒驗證的部分。不貼整份 diff 或完整 log。
5. **逐票驗收（必做）**：每張票交付後，開 `reviewer`（`model: "sonnet"`，跟實作不同的上下文），只給它票檔路徑和 commit，逐條判 PASS／FAIL／UNKNOWN。FAIL 就把理由附在票裡重派；同一張票失敗兩次，收回主 session 重新切票或自己處理。
6. 全部的票都 PASS 之後，照第 5 節對整個完成線做最後一次獨立驗收。

## 5. 獨立驗收

完成線全部打勾後，開一個沒參與實作的 reviewer subagent。給它原始想法、完成線和成果的位置，它要逐條判定 PASS／FAIL／UNKNOWN，並附上證據。有 FAIL 就回到推進迴圈修，修完再審一次。輪數沒有上限，只要每一輪都有進展就繼續；卡關的判斷照第 4 節。

## 6. 回報與保存

- 每推進一段，就在 LOG.md 追加一筆：做了什麼、證據在哪、下一步是什麼。換 session 或換電腦時從這裡接續。
- 收尾回報要分成三類：已完成並驗證、已完成但未驗證、未做。每一類都寫清楚原因。
- 事實、推論、假設要分開標示（[P00](../runtime-reference/policies/P00-GROUNDED-ANSWER.md)）。

## PROJECT.md 格式

```markdown
# <slug>

## 目前狀態（YYYY-MM-DD）
- 模式：目標／方向／種子
- 狀態：進行中／卡關（原因）／完成
- 成果位置：repo、branch、commit
- 下一步：

## 原始想法
> 使用者原話

## 完成線
- [ ] C1 …（怎麼驗證）

## 工具
- Skills：…（為什麼選）
- 角色：…（為什麼選）

## 授權（只記使用者親口說的話，Agent 不能自己填）
- 瀏覽器：未授權／> 使用者原話（日期、在哪次對話說的）
- 對外動作：未授權／> 使用者原話（日期、在哪次對話說的）

## 決策
- YYYY-MM-DD 使用者決定／Agent 判斷（理由）
```

## 需要嚴格控管時

如果使用者要求每一版都固定下來、要獨立准入、要逐檔安全回寫，改用 [Workbench 控制程式](WORKBENCH.md)。這是可選工具，平常不必用。
