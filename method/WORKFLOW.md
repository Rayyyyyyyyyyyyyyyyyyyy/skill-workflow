# 工作流程

使用者給一個**目標**、一個**方向**，或一顆天馬行空的**種子**。Agent 負責到底：自己判斷怎麼做，上網查資料，挑工具，實作，舉證，試錯，一路推進到完成線。只有真正需要使用者的時候才回來問。

## 1. 接案

1. 看 `projects/`，也看 `git branch -a --list '*project/*'`（外部 repo 專案的紀錄在 `project/<slug>` branch 上，要先切過去）。使用者點名的專案，或目標跟既有專案相同，就接續那個專案：先讀它的 `PROJECT.md` 與 `LOG.md`，從「下一步」開始做。舊專案如果沒有「目前狀態」或 LOG.md，就讀它專案資料夾裡現有的文件（含專案自己的 `records/` 子目錄，不是 repo 根目錄的 `records/`），再把 PROJECT.md 補成文末的格式，並補一份 LOG.md。
2. 新目標就建 `projects/<slug>/PROJECT.md`（格式見文末），把使用者原話一字不改貼進「原始想法」。之後的補充往下追加，原文保留。

成果放哪裡：屬於別的 repo 就直接在那個 repo 開 branch 做，紀錄留在這裡的 Project 資料夾；沒有既有 repo 就放 `projects/<slug>/workspace/`。

紀錄 commit 在哪：Project 不是這個 repo 的方法本身，不論成果在別的 repo 還是在 `workspace/`，開工前都先開 worktree：`git worktree add ../skill-workflow-project-<slug> -b project/<slug>`（branch 已存在就去掉 `-b`），`projects/<slug>/` 的修改和 commit 都在那裡做，不要 commit 到 `main`。要 push 也只推 `project/<slug>`；專案結束後用 `git worktree remove` 清掉 worktree，再刪掉本機和遠端的 `project/<slug>` branch，把最後一個 commit 和收尾的兩個數字（第 6 節；分輪做的每一輪各記一組）記進 `records/METHOD_LOG.md`，因為 branch 刪掉後專案自己的 LOG 就不在了。主目錄一直停在 `main`，只放方法本身的修改（`CLAUDE.md`、`method/`、`records/`、`.claude/`、`scripts/` 等），可以直接 commit，push 到 main 前先問。哪個位置由改的檔案決定，不必等使用者說要隔離。

## 2. 判斷是哪一種輸入

| 使用者給的 | 你要做的 | 進入推進迴圈的條件 |
|---|---|---|
| **目標**：要做到的結果 | 自己把目標寫成**完成線**（一條一條可檢查的驗收條件），寫進 PROJECT.md 後直接開工 | 完成線寫好就開工，不必等使用者批准 |
| **方向**：想往哪裡走，終點未定 | 先查資料，提出 2–3 條候選完成線（各附代價與你的推薦），請使用者挑一條，或改成他要的 | 使用者選定完成線，之後就照目標處理 |
| **種子**：天馬行空的想法 | 自己先上網研究可行性、類似作品與技術路線；只問查不到的事（使用者的偏好、可用資源、限制），一輪最多 5 題，每題附上你的建議答案。接著提出 2–3 個具體概念，每個概念都附上它的完成線 | 使用者選定概念，就照目標處理 |

寫完成線前先往上一層想：「這件事做完之後，使用者希望接著發生什麼？」使用者給的常是他猜的做法（「修這個 crash」），背後的結果才是要的（「app 不再當機」）。範圍以使用者原話為界：完成線寫原話範圍內的結果（「這個 crash 的重現步驟跑完不再當機」），不寫做法（「改某個函式」）。往上一層的版本（「app 保持零 crash」）、更好的路線，或發現原本的步驟根本不必存在，只要超出原話，就記進 PROJECT.md 的「決策」，當成選項附推薦問使用者，使用者同意才改完成線；等回覆期間照原話範圍的完成線繼續做。

每條完成線都要寫出**外部判準**：除了 Agent 自己之外，什麼能證明它對，例如測試、可執行的指令或工具、量測數字、沒用過的資料、從原始資料重現，或使用者本人。寫不出外部判準的，改寫成寫得出來的；真的只有使用者能判定（例如喜不喜歡），判準就寫「使用者判定」。寫完成線時用這四問把它挖深：(1) 這一行最頂尖的人會多做什麼？(2) 他們會從哪份最原始的資料開始，而不是別人整理過的版本？(3) 他們用什麼方法與工具？(4) 外部判準是什麼？(1)–(3) 的答案寫進 PROJECT.md 的「工具」欄或完成線本身，(4) 寫在每條完成線後面。

分不出是哪一種時，當成比較成熟的那一種處理，並在回覆裡說明你是怎麼判斷的。使用者明確說要深入討論時，改用 `grilling` 的節奏（要保存決策就用 `grill-with-docs`，它是讀檔型 Skill，直接讀 `.claude/skills/grill-with-docs/SKILL.md`）；這時以 grilling 的一輪規則為準，不受 5 題的限制。

## 3. 挑工具

讀 [CATALOG.md](CATALOG.md)，挑出這次用得上的 Skills 與角色。目錄裡標「讀檔」的 Skill，直接完整讀它的 SKILL.md 再照做。專業角色看 session 的 subagent 類型清單（全域安裝在 `~/.claude/agents/`，清單上就有名稱和一行說明）。挑好的工具和挑選理由寫進 PROJECT.md 的「工具」欄。做到一半發現需要新工具就加上去，同樣記下理由。

使用角色的方式：
- **原生角色**（`.claude/agents/`）：直接當 subagent 類型開。
- **專業角色**（全域 `~/.claude/agents/`）：直接用清單上的名稱當 subagent 類型開，角色內容會自動帶入，不必再讀檔。派工時寫明要它用那一行的哪些方法、工具和原始資料做指定的事。清單上沒有專業角色（例如雲端或新電腦），照 README「另外安裝」裝好；裝不了就只用原生角色，並在 LOG 記下。只換口吻和術語、方法沒變，就是角色扮演，成果不會更好；派工時要寫明要它用哪些方法或工具。
- **跨領域**：在「方向」「種子」模式提候選完成線或概念時，以及同一個問題第二種做法也失敗時，把名詞改寫成動詞（「做簡報」→「在 30 分鐘內讓忙碌的人相信一個因果關係並做出決定」），再列出哪些領域處理過這個動詞，包括專門挑錯的紅隊（例如做空研究員、鑑識會計）。借用的是他們的做法，例如「做空研究員怎麼查證」，不是請 subagent 扮成他們。
- 每個 subagent 都要拿到：目標、完成線、工作目錄、要用的 Skills，以及回報格式（做了什麼、證據、還沒驗證的部分）。
- 彼此獨立的工作可以同時開幾個 subagent 平行做。

## 4. 推進迴圈

進迴圈前先接好**基礎建設**：完成線的外部判準要能讓 Agent 自己跑，例如能取得原始資料、log 或錯誤報告，能對應版本與 commit，有可以重現和驗證的環境。缺的部分先補（有切票時就是第一張票）；需要帳號、金鑰、付費或對外寫入的，照下面的清單先問，需要瀏覽器檢測的，照 CLAUDE.md 護欄取得當次授權。判準跑不起來，題目定得再大也驗收不了。

照下面四步一直循環，直到完成線每一條都有證據：

1. **查**：缺的知識自己找，順序是官方文件、原始碼、網路搜尋，再來是實際試跑。把查到的來源記下來。網路被環境擋住時，先換其他來源；真的需要那個網站，就說明是哪個網站、為什麼需要，請使用者開放網路。
2. **做**：每次推進一小步，做完 commit，讓每一步都能退回。commit 和 push 到這次工作用的 branch 可以直接做，不必問。
3. **驗**：用最貼近真實使用的方式驗證，例如測試、建置、實際執行，或在使用者授權該次檢測後打開瀏覽器看。要留證據：指令與輸出、截圖、數據。
4. **修**：失敗就找出原因，換個做法再試，把試過的做法和結果寫進 LOG.md。

**卡關**是指同一個問題（包含驗收時被判 FAIL 的同一條完成線）換了三種做法都沒進展，或必須取得只有使用者能給的東西。卡關時先把已做的部分保存下來，向使用者說明狀況、列出你想得到的選項並附推薦，然後先做其他不受阻的工作。

以下情況要先問使用者，問了再做：
- 需要帳號、金鑰或付費。
- 部署、發布、推到 main 或預設 branch、開 PR、推到別人的 repo，或其他對外寫入（例如建立 GitHub issue、發訊息）。
- 刪除或覆寫使用者的資料，或其他不可逆的動作。
- 純屬個人喜好、而且會改變方向的選擇。
- 想把範圍擴大到完成線以外。

除了上面這些，其他判斷都由你自己決定，並在 LOG.md 記下理由。

### 切規格與派工（`to-spec` → `to-tickets` → `implement-spec`）

主 session 負責想清楚與切細，執行交給 sonnet，審查用比執行者高一級的 opus。

1. **切規格與票**：主 session 用 `to-spec` 寫 `projects/<slug>/spec.md`，再用 `to-tickets` 切成 `projects/<slug>/issues/NN-<slug>.md`。必填欄位與本 repo 的例外見 [method/agents/issue-tracker.md](agents/issue-tracker.md)。每張票只完成一個可驗證的行為，而且要自足：要做什麼、可能碰到的範圍、不做什麼、驗收指令（可直接執行，看結果就知道 PASS／FAIL）、被哪張票擋住。
2. **明確度關卡**：執行者不必再做判斷就能完成的票，才可以派出去。需要取捨、設計或問使用者的，留在主 session 解決（必要時用 `grilling`），解決後再寫進票。一批票切完後、第一次派工前，開一個全新的 subagent（`model: "sonnet"`），只給它這批票檔的路徑，請它回答：每張票要做什麼、有哪些地方它必須猜。它得猜的地方就補進票裡，補到沒有為止再派工。一批測一次，不逐票測；只問哪裡要猜，不請它審設計。
3. **實作**：用 `implement-spec` 做完整份規格，issue tracker 就是上面那份文件。本 repo 的例外：
   - implementer subagent 用 `Agent(subagent_type: "implementer")`（角色預設 `model: sonnet`），派工訊息只寫票檔路徑、工作目錄和整合 branch，不重抄內容。回報要短：commit hash、跑過的驗收指令和結果、沒驗證的部分。
   - 整合 branch 開在成果所在的 repo；成果在 `workspace/` 時就是 `project/<slug>`，它已經 checkout 在 `../skill-workflow-project-<slug>`，merger subagent 要在那個 worktree 裡合併。
   - 票沒有程式碼（例如文件）時不必用 `tdd`，照票上的驗收指令驗。
   - 開 draft PR 和把它標成 ready for review 都是對外寫入，各自先問使用者；開的話用 `pr` 寫 PR 說明。
   - 最後的 `code-review` 兩個審查 subagent 都用 `model: "opus"`。它找到的問題交給一個 implementer 修，修完再跑一次 `code-review`，直到沒有要修的問題；同一個問題修了兩次還在，就收回主 session 處理。
4. 全部的票完成、`code-review` 沒有要修的問題之後，照第 5 節對整個完成線做最後一次獨立驗收。

## 5. 獨立驗收

完成線全部打勾後，開一個沒參與實作的 reviewer subagent。reviewer 的模型要比執行的 agent 高一級，順序是 haiku、sonnet、opus：執行者是 haiku 就用 `model: "sonnet"`，是 sonnet 就用角色預設的 opus。opus 是上限：執行者是 opus，或是主 session 自己動手改的（例如小幅的方法修改，不論主 session 跑哪個模型），reviewer 都用角色預設的 opus；這兩種情況靠的是獨立的上下文，不是更高的模型。給它原始想法、完成線和成果的位置，它要逐條判定 PASS／FAIL／UNKNOWN，並附上證據。證據照那一條寫的外部判準取得，能跑的就自己重跑，不能用實作者的回報代替；判準是「使用者判定」的，判 UNKNOWN 並註明「待使用者判定」，收尾時列在「已完成但未驗證」，請使用者判定。有 FAIL 就回到推進迴圈修，修完再審一次。輪數沒有上限，只要每一輪都有進展就繼續；卡關的判斷照第 4 節。

## 6. 回報與保存

- 每推進一段，就在 LOG.md 追加一筆：做了什麼、證據在哪、下一步是什麼。換 session 或換電腦時從這裡接續。
- 專案收尾時在 LOG.md 記兩個數字：這個專案裡使用者被問了幾次（Agent 主動停下來問的次數，不算使用者自己發話），以及獨立驗收 FAIL 了幾輪。這是判斷這套方法好不好用的依據。
- 接著用 `retro` 回顧這個專案的 session，把改進候選依嚴重度列給使用者。屬於這套方法本身的，照 CLAUDE.md「方法凍結」處理。
- 收尾回報要分成三類：已完成並驗證、已完成但未驗證、未做。每一類都寫清楚原因。
- 事實、推論、假設要分開標示（[P00](policies/P00-GROUNDED-ANSWER.md)）。

## PROJECT.md 格式

```markdown
# <slug>

## 目前狀態（YYYY-MM-DD）
- 模式：目標／方向／種子
- 狀態：進行中／卡關（原因）／完成
- 成果位置：repo、branch、commit
- 下一步：

## 原始想法
> 使用者原話

## 完成線
- [ ] C1 …（外部判準：用什麼證明，不是 Agent 自評）

## 工具
- Skills：…（為什麼選）
- 角色：…（為什麼選）

## 授權（只記使用者親口說的話，Agent 不能自己填）
- 瀏覽器：這裡不記。每次檢測都要使用者當次授權（見 CLAUDE.md 護欄）
- 對外動作：未授權／> 使用者原話（日期、在哪次對話說的）

## 決策
- YYYY-MM-DD 使用者決定／Agent 判斷（理由）
```
