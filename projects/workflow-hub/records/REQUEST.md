# 原始需求與本次交付範圍

使用者原話：

> 我要讓這個folder變成集合體
> 我有想法丟進來就開在裡面開project套用flow做事

推進偏好：

> 依想法成熟度判斷，需求清楚就直接實作

使用者補充要求：

> 但在開始之前我要確認flow的完整度與可執行程度
> 不是欸？ playbook的定位呢？proof呢？agent role呢？

以下六步已由使用者明確確認「對是這樣沒錯」：

1. 接收想法、建立 project：保存原始目標、限制與已有資料。
2. 判斷成熟度：需求清楚就直接執行；有關鍵缺口才釐清、研究或做原型。
3. 組成 Flow：選擇適用的 Playbooks，安排依賴、交接與交付終點。
4. 配置 Agent Role 與 Skills：Role 承擔專業職責，Skills 提供方法，Playbook 約束工作與交付。
5. 用 Proof 驗收：逐項對照原始要求，查核指定版本與證據；通過才接受、交給下游。
6. 保存並接續：中斷、缺資料或驗收失敗時，保留成果、原因與下一步，避免重新開始。

執行授權：

> 很好 你去開agent來討論並完成這目標

## 實作選擇與限制

三位設計 agents 討論後採用現有 Codex 作實際執行者，標準庫 Python 控制本機狀態與 Proof 接受。這是實作選擇，沒有把使用者授權解讀成發布、付費、瀏覽器測試或解除安全限制。

被刪除的 workflow-mvp 是使用者刻意刪掉的歪掉實作，不能恢復。原兩份設計文件與參考元件保留；尚未實現的隔離/外部操作能力不宣稱完成。

Bootstrap 前期的討論及初稿在新工具完成前產生；計畫將它們列為已有輸入，現在固定工作契約完成整合、實際測試、獨立驗收及下游接手。不能倒填聲稱前期已由本工具派工。
